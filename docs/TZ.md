## 1. Цель и видение

Создать **интерактивную карту** экосистемы 1С.

Главное отличие от обычного списка — **навигация и мнение**:
- фильтры по роли, контексту работы, зрелости, лицензии, происхождению и доступности на рынке РФ;
- карточки с описанием, ответом «зачем» и блоком «с чего начать» (сильная сторона исходного каталога, её сохраняем);
- связи между технологиями (аналоги и зависимости) и отдельная страница графа связей;
- для карточек с репозиторием — автоматические метрики (звёзды, дата последнего коммита) — *реализовано 13.07.2026*: `scripts/repostats.js` собирает по API GitHub/GitLab в статический `app/repostats.js` (запускается вручную, время от времени — как linkcheck), модалка показывает бейджи рядом с лицензией.

## 3. Функциональные требования

- **Карточки** технологий: логотип, краткое описание, метки.
- **Категории и блоки** — отправная структура из README дополнена и уточнена в ходе наполнения. Сейчас 24 категории (поле `categories` в `app/data.js`) сгруппированы в 6 тематических блоков (поле `blocks`):
  - **Проектирование**: Прототипирование · Диаграммы · Моделирование и архитектура · База знаний
  - **Разработка**: Разработка · Библиотеки и инструменты · Плагины и расширения · ИИ-ассистенты · Системы хранения версий · CI/CD
  - **Качество**: Автоматизированное тестирование · Статический анализ кода · Код-ревью
  - **Инфраструктура и эксплуатация**: Администрирование 1С · Сетевая инфраструктура и облако · Безопасность · СУБД · Мониторинг · Производительность и нагрузочное тестирование
  - **Данные и интеграции**: Интеграции · API и веб-сервисы · BI-системы
  - **Управление и компетенции**: Задачи · Сертификация
  - **Пороги ёмкости** (чтобы схема-постер читалась): подкатегория — не более **9** инструментов, раздел — не более **6** категорий. Превышение — повод разбить подкатегорию или завести новый раздел. Оба порога жёсткие, их проверяет `scripts/validate.js`; правила разметки — в [`METHODOLOGY.md`](METHODOLOGY.md) («Ёмкость подкатегорий и разделов»).
- **Фильтры и поиск** (две независимые оси — функция и контекст — плюс три скалярные метки и доступность):
  - **функциональная роль** (*что делаешь*): разработчик / администратор / аналитик / тестировщик (роль «администратор» включает devops/эксплуатацию);
  - **контекст работы** (*где/как работаешь*): франчайзи / инхаус / продукты / проекты (бывший «фриланс» влит во «франчайзи»);
  - **зрелость**: `базовое` / `продвинутое` / `нишевое` ;
  - **лицензия**: open-source / бесплатное / проприетарное;
  - **происхождение**: отечественное / зарубежное (импортозамещение);
  - **доступность** на рынке РФ: доступен / ограничен (отдельно от происхождения).
  Подробнее про поля см. METHODOLOGY.md
- **Деталь карточки** (модалка): описание, «зачем», «с чего начать», ссылки; для карточек с репозиторием — авто-метрики (звёзды, дата последнего коммита). Открытая карточка отражается в URL (`?tool=имя`) — дип-линки для шаринга работают на главной, графе и схеме.
- **Виды отображения**: ландшафт (карточки) + граф связей + схема-постер + путь освоения;
- **Аналитика с разрешения посетителя** — *реализовано 07.09.2026, сценарий уточнён 20.09.2026*: общий `app/analytics.js` подключает базовую Яндекс Метрику только после явного разрешения; Вебвизор, карта кликов, ecommerce и `noscript`-пиксель отключены. Выбор хранится локально в `landscapeAnalytics`. На главной запрос появляется после первого открытия и закрытия карточки инструмента, когда посетитель уже успел попробовать основной сценарий. Простое описание данных и контакта оператора — `app/privacy.html`.
- **Embed** карточек на внешние сайты — *решили не делать (13.07.2026)*.

## 4. Модель данных

Данные живут в `app/data.js` — глобальный объект `window.LANDSCAPE` (`categories`, `blocks`, `axes`, `items`). Одна карточка из `items`:

```js
{
  name: "1C: Platform Tools",
  added: "2026-06-10",             // дата добавления в ландшафт (ISO); редактор ставит сам
  updated: "2026-06-27",           // дата последней правки карточки (ISO); редактор штампует при любом изменении
  category: "Разработка",          // одна из categories
  subcategory: null,
  description: "Расширение VSCode: инструменты разработки 1С в одной панели",
  why: "Не переключаться между утилитами при разработке около-1С проектов",
  logo: "1c-platform-tools.svg",   // файл в app/logos/; null → заглушка «1С»
  homepage: "https://marketplace.visualstudio.com/items?itemName=yellow-hammer.1c-platform-tools",
  repo: "https://github.com/yellow-hammer/vscode-1c-platform-tools", // → авто-метрики (app/repostats.js)
  start: ["Marketplace: …", "Репозиторий: …"],   // блок «с чего начать»
  maturity: "продвинутое",         // базовое | продвинутое | нишевое
  roles: ["разработчик", "администратор"],        // функциональная роль (массив)
  contexts: ["инхаус", "продукты"],               // контекст: франчайзи|инхаус|продукты|проекты
  origin: "отечественное",         // отечественное | зарубежное
  license: "open-source",          // open-source | бесплатное | проприетарное
  availability: "доступен",        // доступен | ограничен (доступность на рынке РФ)
  analogs: ["…"],                  // взаимозаменяемые (симметрично)
  depends: ["…"],                  // «зависит от» (направленно)
  aliases: ["гит", "git hub"],     // скрытые поисковые синонимы (рус. транслитерации и пр.)
  hidden: true,                     // убрать из обычных представлений ландшафта, оставить в поиске
  hiddenReason: "…"                // причина скрытия на карточке и SEO-странице
}
```

Скрытые карточки исключаются из доски без поискового запроса, графа, схемы и пути.
Их можно найти внутренним поиском; статические страницы карточек остаются в sitemap
и доступны через внешние поисковики. Статус «Скрыта с карты» выделен красным бейджем
в результатах поиска, детальной карточке и на статической странице; рядом указана причина.
Исходные данные сохраняются в `app/data.js`. Валидатор требует булев `hidden`,
непустую строку `hiddenReason` для скрытой карточки и запрещает причину у видимой.
В публичных текстах используем «опрос сообщества 2026», без упоминания волн.
Причины скрытия начинаются с «По итогам опроса сообщества 2026».

**Инвариант значений:** строковые метки в карточке должны точно совпадать со значениями в `axes.<ось>.values` — иначе фильтр не сработает. Целостность проверяет `scripts/validate.js`.

## 6. Контекст работы: стартовые наборы

Контекст работы 1С-разработчика заметно меняет набор инструментов. Реализовано меткой-осью `contexts` на элементах:

| Контекст | Что в фокусе | Характерные инструменты |
|---|---|---|
| **Франчайзи** (+ фриланс) | много клиентских баз, типовые, обновления, быстрые доработки; минимум инфраструктуры | Конфигуратор, ИТС, расширения, многобазная обработка, обмены, портативные инструменты, Infostart Toolkit |
| **Инхаус** | одна компания, глубокая поддержка и интеграции | EDT+git, мониторинг (Zabbix/Prometheus), брокеры, S3, кластер |
| **Продукты** (тиражные решения) | релизы, совместимость версий, качество | git, CI/CD (Jenkins/GitLab), Vanessa/YAxUnit, SonarQube/BSL LS, OPM, публикация на Инфостарт |
| **Проекты** (внедрение) | методология, крупные внедрения, нагрузка | СППР, EnterpriseData/Шина, 1С:КИП/ЦКК, нагрузочное тестирование, документирование |

Это не жёсткие границы, а ориентир: один инструмент может попадать в несколько контекстов.

## 8. Почему не готовый движок (landscape2)

Сначала пробовали [landscape2](https://github.com/cncf/landscape2) (движок CNCF Landscape: YAML → статика, авто-метрики GitHub). Прототип показал, что он не закрывает ключевую идею проекта:

- **Кастомные фильтры не поддерживаются.** Набор фильтров фиксирован (категория, зрелость, лицензия, организация, страна + общий `TAG`). Наши две оси (роль + контекст) чисто отфильтровать нельзя; кастомные поля движок принимает, но не использует ни в фильтрах, ни на карточках.
- **Нет локализации UI.** Обвязка интерфейса — на английском, что конфликтует с решением «только русский».

**Итог: от landscape2 отказались**, артефакты разведки (его `landscape.yml`/`settings.yml` и сборку) удалили из репозитория.

## 9. Архитектурное решение

**Делаем свой статический фронтенд.** Две оси фильтров (роль + контекст) + зрелость/происхождение/лицензия/доступность, полностью русский UI, связи и граф. HTML/CSS/JS без сборки и зависимостей, данные — `window.LANDSCAPE` в `app/data.js`. Деплой статикой на GitHub Pages.

## 10. Связи между технологиями (реализовано, включая граф)

Связи превращают каталог в карту и дают навигацию «что дальше».

**Реализовано.** Два типа связей, по образцу схемы из StackTechnologies1C (`img/stacktechnology.png`):
- **Аналоги** — взаимозаменяемые инструменты (`RabbitMQ ↔ Kafka`, `Конфигуратор ↔ EDT ↔ VSCode`, СУБД между собой).
- **Зависимости** — связанные по необходимости (`EDT — git`, `Хранилище — Конфигуратор`, плагины → их хосты, `Kibana/Logstash → Elasticsearch`).

**Модель (фактическая).** У элемента два поля-массива `analogs` и `depends` (имена связанных карточек):
- **`analogs` — симметричны**: прописываются на обоих концах. Группируются по близости («простые» и «сложные» внутри одной категории связываются раздельно, а не все-со-всеми).
- **`depends` — направленные («зависит от»)**: A → B означает «чтобы осмысленно работать с A, нужен и B», и так выстраивается цепочка (IDE → git → Хранилище). Прописываются только на исходном конце.

В детальной модалке (`detail.js`) — блоки «Аналоги»/«Зависимости» с квадратными кнопками (лого + название), клик открывает связанный инструмент. На 15.10.2026 в данных связи проставлены у 182 карточек (аналоги) и 84 (зависимости). Скрытые карточки исключаются из отображаемых связей. Целостность связей проверяет `scripts/validate.js`.

**Граф связей (реализован).** Отдельная страница `graph.html` (`graph.js`): force-directed canvas-граф по `analogs`/`depends` с фильтрами по роли и зрелости, тёмной темой и поддержкой тач-жестов на узких экранах. Клик по узлу открывает ту же детальную модалку, что и на главной.

**Схема-постер (реализована).** Отдельная страница `scheme.html` (`scheme.js`) — статичное древо «блок → категория → карточки инструментов», целиком в одном инлайн-SVG. Отбор по роли/зрелости и скрытие блоков, клик по карточке открывает ту же модалку. Экспорт без зависимостей: SVG (вектор), PNG/PDF (через canvas), майндмап `.mm` (FreeMind). Назначение — выгрузка карты картинкой/вектором (в т.ч. для печати и Illustrator).

**Отличия от первоначального плана.** Свели 5 предложенных типов к двум (аналоги/зависимости) — этого достаточно для навигации и совпадает с авторской схемой. Сделана направленность зависимостей и полноценный граф. Редактирование связей в `editor.html` — реализовано (аналоги двусторонние, зависимости односторонние).

## 11. Слой компетенций и грейдов («Путь» реализован, слой грейдов заморожен)

**Вид «Путь» — реализован** (`path.html` + `path.js`): маршрут освоения инструментов для выбранной роли без матриц компетенций, на уже размеченных данных. Ступени — шкала зрелости (База → Мейнстрим → Специализация), внутри ступени группировка по блокам ландшафта; отметки «знаю» с прогрессом хранятся в localStorage (`pathKnown`), роль — в URL (`?role=…`). Клик по инструменту открывает общую модалку. Ограничение зафиксировано на странице: путь подсказывает «что учить», но не заменяет учебу.

**Полный слой грейдов (Junior/Middle/Senior) — заморожен.** Эксперимент проведен в ветке `feature/competencies` (итог — `89c810f`): для одной роли грейд практически совпадает со шкалой зрелости, отдельный слой не добавляет ценности поверх «Пути». Замысел (компетенция ↔ технологии, компетенция ↔ грейд, вид «Грейд») сохраняем на случай появления качественных матриц компетенций; код и разметку в main не вливаем. Исследование перенесено в main как документация — `docs/archive/competencies/` (README с итогом, coverage.md, draft-grades.md, исходники матриц; 14.07.2026), кодовый эксперимент (разметка грейдов в `data.js`, ступени в `path.js`, `scripts/grades.js`) остается только в ветке. Туда же смотрит заготовка роадмапа обучения — `docs/archive/roadmap/README.md` (исследование 15.06.2026, влито в main 14.07.2026).

## 12. Экспертность, контрибьюторы и методология (частично реализовано)

Ценность ландшафта — в мнении (зрелость, рекомендации, связи), а мнению нужна видимая экспертиза. Делаем ставку на коллективную экспертизу уважаемых в сообществе людей, а не одного автора.

**Согласие (обязательно, до публикации).** Фото, имя и контакты любого человека — только с явного разрешения. Ссылаться на публичные профили (Telegram, GitHub, Инфостарт), а не на личные контакты; аватар — только с согласия. Процесс: короткое согласование «как это будет выглядеть» + ссылка на черновик.

**Как показываем экспертность (вводим постепенно):**
1. **Экспертный совет** — *реализован* (`council.html`): страница с кураторами (фото, имя, био, область курирования) и автором проекта. Сейчас 8 кураторов (разработка ×2, аналитика ×2, тестирование ×2, администрирование, инфраструктура) + автор; фото лежат в `app/people/`. Расширяется по мере согласия новых людей.
2. **Контрибьюторы** — открытый список всех участников (как в awesome/CNCF), мотивирует вносить вклад. *Отложено на потом (13.07.2026).*
3. **Атрибуция оценок** — «категорию курировал X», «метку зрелости подтвердили …» (приём Thoughtworks Tech Radar). *Пока не делаем — кураторы и так видны на странице совета; вернёмся при необходимости (13.07.2026).*

**Страница «Методология»** — *реализована* (`methodology.html`): как принимаются решения, как размечены оси, как предложить правку. Прозрачность = доверие. Рабочая версия правил разметки осей (роль, контекст, зрелость, происхождение, лицензия, доступность) и сравнение с другими ландшафтами ведётся в [`METHODOLOGY.md`](METHODOLOGY.md).

**Модель данных:** `experts: [{ name, role, photo, links, areas }]`; опционально `curatedBy` у категорий/элементов. Реализация — статикой.

**Порядок:** прототип, связи, разделы «Экспертный совет» и «Методология» — сделаны. Дальше: согласовывать новых экспертов; список контрибьюторов — отложен.

## 13. Популярность у сообщества (итоги 2026 опубликованы)

Экспертную разметку дополняют данные о знакомстве с инструментами и опыте их
применения. Ответ «работал» означает опыт когда-либо, а не текущее использование.
Опрос не меняет зрелость автоматически: решения автора и кураторов собраны в
[журнале пересмотра](decisions/2026-survey.md).

### Состояние данных

- Сбор завершен 01.10.2026; оба бота закрыты для новых ответов (`CLOSED=1`).
- Итоговый набор `app/survey2026.js` содержит 215 инструментов: 202 из снимка
  30.09.2026 (316 участников) и 13 дополнений из июля. Результаты одного
  инструмента и участники разных источников не складываются.
- В публичных текстах используем «опрос сообщества 2026»; пометка «Июль 2026»
  уточняет дату источника данных. История снимков — в
  [журнале результатов](surveys/2026/results.md).
- Опубликованы обезличенные агрегаты. Публикация сырого датасета остается задачей
  после проверки состава полей и рисков идентификации участников.

### Источники и публикация

Все страницы, `scripts/validate.js` и `scripts/sitegen.js` читают только
`app/survey2026.js`. `node scripts/survey-publish.js` готовит его из архивных
`data/surveys/2026/july.json` и `september.json`. Объединение выполняется при
подготовке файла; индексы сегментов приводятся к общим словарям. Сборка
`node scripts/build.js` также запускает подготовку опроса.

`bot/aggregate.js` по умолчанию пишет игнорируемый `app/survey2026-live.js`.
`./survey-live.command` получает журнал с сервера потоком, сохраняет только
агрегаты и открывает `survey2026.html?data=live` на localhost. Этот явный
предпросмотр показывает локальный снимок; без параметра сайт использует
опубликованные данные. Автоматической подмены на localhost нет.

### Опрос и метрики

- Первый вопрос: «работал» / «слышал» / «не знаю». После «работал» — необязательный
  «использовал бы снова?», после «слышал» — «хочешь попробовать?».
- Узнаваемость = работали или слышали / все ответы по инструменту;
  использование = работали / все ответы. Возврат и интерес считаются только
  от ответивших на соответствующий второй вопрос; пропуск не считается «нет».
- Профиль: роль, уровень, контекст работы. Очередь зависит от роли и зрелости;
  контекст используется для сегментации, не для выбора инструментов в очереди.
- Боты Telegram (long polling) и MAX (webhook) используют общее ядро и раздельные
  сессии. Поддерживаются пауза, продолжение и исправление ответов. Журнал
  `answers.jsonl` дописывается; последний ответ респондента по инструменту
  имеет приоритет. Идентификаторы хешируются с солью, пространства Telegram и
  MAX различаются; объединения аккаунтов между платформами нет.
- В карточках проценты показываются от 3 ответов в знаменателе метрики.
  На витрине второй вопрос также имеет порог 3; строки с менее 10 ответами
  приглушаются, квадрант требует не менее 5 работавших и 5 оценок возврата.
- Фильтры витрины: роль, уровень, контекст; ИЛИ внутри оси, И между осями,
  пустой выбор означает «все». Сегментация используется вместо взвешивания.
- В основной выборке 235 разработчиков, 63 аналитика, 15 администраторов и
  3 тестировщика. Состав ограничивает выводы об инфраструктуре и тестировании.

## 14. Инструмент редактирования и разметки (реализован)

Править данные напрямую в `app/data.js` (бегать по JSON руками) неудобно и чревато ошибками: легко опечататься в значении метки, рассинхронить его с `axes.*.values`, забыть поле. Нужен **визуальный редактор разметки**.

Идея — тот же вид, что и основной ландшафт (сетка карточек), но в **режиме редактирования**:
- менять метки осей (`роль / контекст / зрелость / происхождение / лицензия`) кликами по чипам, а не текстом;
- редактировать `name / description / why / start / связи` в форме карточки;
- **валидация по инварианту значений**: метки выбираются только из допустимых `axes.*.values`, рассинхрон невозможен;
- добавление и удаление карточек.

Вывод — **экспорт обратно в формат `app/data.js`**, чтобы результат можно было закоммитить.

**Реализовано** (`app/editor.html` + `editor.js`): сетка карточек в режиме редактирования, метки осей кликами по чипам с валидацией по `axes.*.values`, добавление/удаление карточек. По кнопке «Сохранить» весь `window.LANDSCAPE` сериализуется обратно тем же 2-пробельным JSON и пишется прямо в `app/data.js` — для записи нужен лёгкий пишущий сервер `scripts/serve.py` (POST `/save`); без него «Сохранить» откатывается на скачивание копии. Дата `updated` файла (`LANDSCAPE.updated`) проставляется автоматически; кроме того, при любой правке карточки редактор штампует ей `updated` (для двусторонних аналогов — и парной), а новые карточки получают `updated` = дате создания. Пока поле только собирается, в UI не показывается — задел под историю изменений и сводку «что нового с даты X». При ручной правке `data.js` дату ставь сам; `validate.js` ловит карточки без корректной `updated`.

### Автоматические проверки и публикация

Версия Node.js для разработки и CI задана в `.node-version` (24). Workflow
`validate.yml` выполняет валидацию каталога, проверку очередей бота, все тесты
`bot/test/*.test.js` и `tests/*.test.js`, затем сборку публичного сайта.
`deploy.yml` выполняет эти же проверки перед отправкой артефакта в GitHub Pages;
любой неуспешный шаг останавливает публикацию. Оба workflow используют
Ubuntu 24.04 и актуальные действия GitHub с Node.js 24.
