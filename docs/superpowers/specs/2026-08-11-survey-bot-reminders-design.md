# Напоминания брошенным сессиям опроса (@stateOf1c_bot)

Дата: 2026-08-11
Статус: одобрено, ожидает плана реализации

## Контекст

Бот-опросник [`bot/`](../../../bot/README.md) готовится к боевой волне (сентябрь 2026, см. память `landscape-survey-launch-plan`). Опрос длинный (десятки карточек по роли), часть респондентов будет бросать его на середине. Сейчас у бота нет никакого механизма напомнить и позвать вернуться — есть только ручная разовая рассылка `bot/notify.js` (шлёт один текст всем адресатам из `state.json`, без разбора кто дошёл до конца, а кто нет) и `bot/funnel.js` (только аналитика воронки для мониторинга, ничего не отправляет).

Нужен автоматический механизм: заметить, кто застрял посреди опроса, и напомнить.

## Цели

- Автоматически находить сессии, которые «зависли» посреди опроса (ответили хотя бы на один вопрос, но давно не возвращались).
- Слать напоминание с прогрессом и кнопкой «Продолжить», ведущей обратно в тот же экран, что и обычное `/resume`.
- Не заспамить: максимум два напоминания на человека за волну.
- Не конфликтовать с работающим ботом (никакой гонки за `state.json`).

## Не цели

- Не трогаем тех, кто не ответил ни на один вопрос (бросил на выборе роли/уровня/контекста) — по решению пользователя это разный тип отвала, не в этой задаче.
- Не меняем логику самого прохождения опроса — только зовём вернуться в уже существующие экраны (`quiz`/`paused`/`checkpoint`/`fix`).
- Не строим сложный конвейер кампаний — только два фиксированных напоминания.

## Данные — изменения в сессии

`bot/lib/store.js` уже хранит сессию как `state[chat]` (реальный `chat_id` → объект). Добавляется одно новое поле, которое пишет **сам `bot.js`** (единственный писатель `state.json`, как и сейчас):

- `s.lastActive` — `Date.now()`, проставляется в начале `onMessage`/`onCallback` в `bot.js` при любом входящем действии пользователя (текст, кнопка, ответ на карточку). Одна точка простановки — в начале роутинга, до всех веток `if`.

Прогресс не требует новых полей — уже есть `s.pos` и `s.queue.length`.

## Кого считаем «зависшим»

Сессия попадает в рассмотрение, если:

- `s.step` ∈ `{"quiz", "paused", "checkpoint", "offer", "fix"}` — в процессе опроса, не `"done"`, не `"closed"` и не стадии онбординга (`"intro"`, `"role"`, `"level"`, `"context"`);
- `s.answered.length >= 1` — ответил хотя бы на один вопрос (защита на случай рассинхрона `step`/`answered`, основной фильтр — по `step`).

## Два напоминания

**Первое — реактивное, по бездействию.**
Триггер: `Date.now() - s.lastActive >= 3 дня` (72 часа), напоминание ещё не отправлено (`reminders[chatId].count === 0` либо записи нет).

**Второе — календарное, «последний шанс».**
Разовая рассылка примерно за 7 дней до объявленной отсечки волны (дата отсечки — константа в скрипте, выставляется при запуске волны). Уходит всем, кто всё ещё не `"done"` (независимо от точного времени бездействия — раз волна заканчивается, это финальный призыв), у кого `reminders[chatId].count < 2`.

После второго напоминания — `count` становится `2`, дальше сессия не трогается никогда, даже если человек ещё раз проявит активность и снова замрёт.

## Текст напоминания — два варианта

- Для `s.step === "paused"` — «ты сам поставил на паузу» (дружелюбное «как обещал, напоминаю»).
- Для остальных шагов из списка выше — «заметили, что прогресс завис» (без упоминания паузы).

Оба варианта включают прогресс (`s.pos` из `s.queue.length`) и инлайн-кнопку «Продолжить». Тексты пишет сам пользователь (как и весь остальной контент бота) — в реализации оставить понятные плейсхолдеры-константы в `lib/texts.js`, не сочинять финальную формулировку за него.

## Кнопка «Продолжить»

`callback_data`, заводящий в уже существующий унифицированный путь резюме — тот же переход, что сейчас обрабатывают текстовые `RESUME_WORDS` и колбэк `kind === "resume"` для `paused`/`checkpoint`/`quiz`/`fix`. Новой логики прохождения не добавляется, только новая точка входа в неё.

## Учёт отправленных — отдельный файл, не `state.json`

`state.json` перезаписывается работающим ботом каждую секунду из его собственной памяти (`flushState` в `store.js`, debounce 1с, tmp+rename). Если бы `remind.js` писал счётчик прямо в `state.json`, следующий флаш живого процесса бота затёр бы правку — гонка данных.

Решение: `remind.js` ведёт отдельный файл `bot/reminders.json` (в `.gitignore`, по аналогии с `answers.jsonl`/`state.json`/`file-ids.json`), формат:

```json
{ "<chatId>": { "count": 1, "lastSentTs": 1755000000000 } }
```

`remind.js` читает `state.json` **только на чтение**, пишет исключительно в свой файл — гонок с ботом нет вообще.

## Отправка

Скрипт `bot/remind.js`, по образцу `bot/notify.js`: напрямую через `api("sendMessage", ...)` из `bot/lib/telegram.js`, без запуска polling-цикла бота (бот и скрипт — разные процессы, это ок, т.к. они не оба слушают апдейты).

Флаги как у `notify.js`:
- по умолчанию — репетиция (`--dry-run`, т.е. без `--yes` ничего не уходит, только лог кому и что),
- `--yes` — реальная отправка.

Пауза между сообщениями (429 от Телеграма ретраится, как везде — уже в `lib/telegram.js`). Блокировка бота пользователем — не ошибка, просто пропуск (как в `notify.js`).

## Запуск: cron на сервере

```
0 10 * * * cd /opt/landscape1c/bot && node remind.js --yes >> /var/log/remind.log 2>&1
```

Раз в день; внутри скрипта своя логика решает, кому реально сегодня уходит первое/второе напоминание — холостой прогон (никому ничего не подошло) ничего не отправляет.

Перед включением в cron — ручной прогон с `--dry-run` на проде, свериться со списком адресатов и текстом.

## Безопасность и идемпотентность

- Максимум 2 напоминания на `chatId` за волну — жёсткий счётчик в `reminders.json`, без сброса.
- `remind.js` никогда не пишет в `state.json` и не создаёт сессий — только читает.
- Если `reminders.json` отсутствует — считается пустым (никому ничего не отправлено), скрипт создаёт файл при первой записи.
- Блокировки/удалённые чаты — пропуск, не ошибка, не ретрай.

## Тестирование

- Юнит-уровня нет (в проекте нет юнит-тестов, `bot/validate.js` — единственная самопроверка, см. `CLAUDE.md`).
- Проверка вручную: прогнать `--dry-run` на тестовых данных (можно временно проставить `s.lastActive` в прошлое в локальном `state.json` для теста), свериться со списком и текстом.
- После деплоя на прод — один ручной `--dry-run`, свериться с реальным `state.json`, только потом добавлять cron.
