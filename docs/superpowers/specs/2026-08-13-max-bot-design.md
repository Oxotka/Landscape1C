# Бот опроса в мессенджере MAX

Дата: 2026-08-13
Статус: реализовано и проверено живым прогоном в MAX

## Контекст

Опросный бот [@stateOf1c_bot](https://t.me/stateOf1c_bot) (`bot/`, см. `bot/README.md`)
собирает данные о востребованности инструментов ландшафта в телеграме,
сейчас заморожен (`CLOSED=1`) до боевой волны в сентябре 2026 (память
`landscape-survey-launch-plan`). Дублирование в MAX исследовано заранее и
осознанно отложено: issue [#26](https://github.com/Oxotka/Landscape1C/issues/26)
зафиксировал требования платформы и рекомендовал вернуться к вопросу при
подготовке следующей волны. Час настал — цель этой спеки: полный порт бота
в MAX **к сентябрьской волне**, чтобы MAX-бот стартовал одновременно с
телеграм-ботом.

На момент написания спеки: самозанятость для регистрации бота есть,
бот создан в MAX и **прошёл модерацию** — готов к разработке.

## Цели

- Тот же опрос, то же ядро логики, в MAX — без дублирования бизнес-логики
  под каждую платформу.
- MAX-бот и телеграм-бот запускаются и работают независимо друг от друга
  (падение/перезапуск одного не роняет другой).
- Респондент опознаётся раздельно по платформам — сшивку личности между
  телеграмом и MAX не строим (см. «Не цели»).
- Инфраструктура для вебхука разворачивается на существующем VPS, без
  нового сервера.

## Не цели

- Не боремся с задвоением респондентов (человек прошёл опрос и в
  телеграме, и в MAX — це два независимых ответа с разным `uid`).
  Решение зафиксировано с пользователем: в `answers.jsonl` добавляется
  поле `platform`, возможное небольшое задвоение в агрегатах — приемлемая
  погрешность выборки.
- Не переписываем сам опросный контент/вопросы — MAX получает тот же
  квиз, что и телеграм.
- Не решаем красивый ник бота — MAX выдаёт `id<ИНН>_bot` автоматически,
  это ограничение платформы, не обходим.

## Архитектура: общее ядро, два транспорта

Бизнес-логика (`bot.js`, `lib/quiz.js`, `lib/texts.js`, `lib/logos.js`)
остаётся одна на обе платформы. Два независимых процесса:

- `bot.js` — как сейчас, long polling телеграма;
- `bot-max.js` (новый) — тонкий HTTP-приёмник вебхука MAX за nginx
  (порт 443 снаружи — MAX на практике не доставляет вебхуки на
  нестандартные порты, `127.0.0.1:3001` внутри): принимает событие,
  собирает из него **тот же telegram-подобный конверт**, который уже
  ожидают `onMessage`/`onCallback` (`{chat: {id}, message_id, text}`
  для сообщений, `{id, data, message: {chat: {id}, message_id,
  photo}}` для колбэков), и напрямую зовёт их.

Уточнение относительно первой версии спеки: вместо изобретения нового
нормализованного формата и переписывания под него сотен строк
`onMessage`/`onCallback` (десятки обращений к `m.chat.id`,
`q.message.message_id`, `q.data` и т.п. по всему файлу) — дешевле и
безопаснее для боевого бота притвориться, что событие MAX выглядит как
telegram-update. `onMessage`/`onCallback` не меняются вообще, кроме
самих вызовов `api()` с telegram-специфичными методами (см. ниже).
Единственная правка в `bot.js`: экспортировать `onMessage`/`onCallback`
(`module.exports = { onMessage, onCallback }`) и обернуть текущий блок
«── Long polling ──» (низ файла) в `if (require.main === module) { ... }`
— иначе `require("./bot")` из `bot-max.js` запустит вторую telegram-сессию
long polling внутри MAX-процесса (два polling на один токен дерутся за
апдейты — этого нужно избежать).

### Транспортный контракт — расширение, не замена

Текущий контракт транспорта (`lib/telegram.js`) — `{api, send, sendPhoto,
hideCard, toast}`. Проверка кода показала, что `bot.js` в нескольких
местах обходит этот контракт и напрямую зовёт `api()` с
telegram-специфичными именами методов и формой параметров:
`editMessageText`/`editMessageCaption` (строки ~89, ~654),
`answerCallbackQuery` (~541), `setMyCommands`/`setChatMenuButton`
(~790–806). Это и есть реальный объём рефакторинга — не «подставить
другой транспортный модуль», а убрать прямые обращения к `api()` из
`bot.js` и завести именованные функции в контракте:

- `editCard(chat, msgId, text, keyboard, isPhoto)`,
- `answerCallback(id)`,
- `setupCommands()`.

`lib/telegram.js` реализует их поверх текущих telegram-методов,
`lib/max.js` (новый) — поверх REST MAX Bot API на
`https://platform-api2.max.ru` (уточнено по документации, 14.08.2026):
`POST /messages?chat_id=…` — отправка, `PUT /messages?message_id=…` —
редактирование, `DELETE /messages?message_id=…` — удаление,
`POST /uploads` — загрузка фото (возвращает `token` вложения),
`POST /answers?callback_id=…` — ответ на нажатие кнопки (аналог
`answerCallbackQuery`, опционально с тем же телом `message`, что и
отправка — можно одним вызовом и подтвердить, и заменить карточку).
Токен — в заголовке `Authorization: <token>` (query больше не
поддерживается). `bot.js` и общее ядро зовут только именованные функции
контракта и ничего не знают
про конкретную платформу.

Ошибки редактирования/удаления транспорт глотает сам —
`hideCard` в `lib/telegram.js` уже делает `.catch(()=>{})`; `lib/max.js`
следует тому же паттерну для `editCard`/`hideCard`. Это важно из-за
ограничения MAX ниже (24-часовое окно).

## Хранилище: платформа в uid / state / answers

Точечные правки `lib/store.js`:

- `uid = sha256(SALT + platform + id)` — без префикса платформы разные
  мессенджеры теоретически могут выдать пересекающиеся числовые id и
  молча слить двух разных людей в одну карточку ответов в `index`;
  с решением «не бороться, но помечать platform» это всё равно нужно
  делать правильно, иначе появится тихий баг задвоения наоборот
  (слияние, а не дублирование);
- раздельные файлы состояния сессий: `state.json` (телеграм) и
  `state-max.json` (max) — оба процесса пишут state раз в секунду
  (`flushState`), общий файл — гонка данных между процессами;
- `answers.jsonl` остаётся общим (по решению — не бороться с
  задвоением), в каждую запись добавляется `platform: "telegram" |
  "max"`;
- `reminders.json` тоже разделяется по платформе — набор `chatId`
  у платформ не пересекается по смыслу, отдельные файлы проще, чем
  один файл с составным ключом.

`report.js`/`aggregate.js`/`funnel.js` не меняются в главной цели этой
спеки: если понадобится срез по платформе — отдельная небольшая задача
после запуска, не блокирует порт.

## Инфраструктура (тот же VPS)

MAX требует вебхук по HTTPS с сертификатом от доверенного CA (голый HTTP
и самоподписанные сертификаты отключат 25.05.2026) — long polling только
для разработки. Документация MAX порт явно не регламентирует, но **на
практике это неверно**: живой прогон 14.08.2026 показал, что вебхук на
нестандартном порту (`8443`) MAX ни разу не доставил (ни одной попытки
соединения в логах nginx за много часов), а на `443` доставка заработала
сразу же. Порт — жёстко **443**, без исключений.

Изначально `443` на VPS был занят личным VPN-сервисом владельца (`xray`,
VLESS+Reality под видом `www.icloud.com`, systemd-юнит `xray.service`).
По решению владельца этот VPN больше не нужен — `xray.service` **выключен
и отключён от автозапуска** (`systemctl disable`, конфиг не удалён, можно
включить обратно `systemctl enable --now xray` при необходимости), порт
443 полностью отдан MAX-боту.

- Поддомен, например `max-bot.landscape1c.ru` — DNS A-запись на IP
  VPS. Основной домен обслуживается GitHub Pages (сайт), поддомену это
  не мешает — отдельная A-запись, не трогает существующий CNAME/A
  апекса.
- На VPS — nginx как TLS-терминатор + certbot (Let's Encrypt) на `443`,
  проксирует на локальный порт `127.0.0.1:3001`, где слушает
  `bot-max.js` (сам процесс — голый http, без TLS-логики в коде).
  Настроен и слушает также `8443` (оставлен как есть, не мешает —
  реального трафика туда MAX не шлёт).
- Фаервол фактически открыт (`ufw` выключен, `iptables` без явного
  дропа кроме fail2ban на 22-м порту) — новый порт открывать отдельно
  не потребовалось.
- Новый systemd-юнит `stateof1c-max.service` рядом с существующим
  `stateof1c.service` (по образцу `bot/deploy/stateof1c.service`).
- Исходящие запросы к `platform-api2.max.ru` (регистрация вебхука,
  отправка сообщений) требуют доверия к российскому CA — сертификат
  MAX подписан «Russian Trusted Sub CA» (Минцифры), которого нет ни в
  системном хранилище Ubuntu, ни (что важнее) в собственном наборе CA
  Node.js. На VPS установлены `russian_trusted_root_ca`/`_sub_ca` в
  `/usr/local/share/ca-certificates/` (`update-ca-certificates`) — для
  системных инструментов (curl, openssl); для Node.js отдельно нужен
  `NODE_EXTRA_CA_CERTS=/etc/ssl/certs/russian-trusted-ca.pem` (объединённый
  PEM обоих сертификатов) — прописан в `/etc/stateof1c.env`, подхватывается
  всеми процессами через `EnvironmentFile`.
- Реальная схема webhook-payload (снята 14.08.2026, в документации MAX
  не публикуется): `chat_id` и `mid` лежат не на верхнем уровне
  объекта `Update`, а вложенно — `update.message.recipient.chat_id`,
  `update.message.body.mid`, `update.message.body.text` (для
  `message_created`); для `message_callback` — `update.callback.callback_id`,
  `update.callback.payload`, тот же `update.message.recipient.chat_id`/
  `update.message.body.mid` карточки с кнопкой. Перевод в
  telegram-подобный конверт для `onMessage`/`onCallback` — в `bot/bot-max.js`.

## Регистрация бота

- Верификация самозанятости на business.max.ru — **сделано**, бот
  создан и **прошёл модерацию**.
- Ник бота — авто `id<ИНН>_bot`, не настраивается; красивое имя и
  описание — в профиле бота (что бот умеет ограничено настройками,
  которые платформа даёт).
- Токен — хранится в `/etc/stateof1c.env` на VPS рядом с
  телеграм-токеном (по аналогии с текущей практикой).

## Эксплуатационные скрипты

`remind.js` и `notify.js` сейчас жёстко привязаны к телеграм-транспорту
и к единственным `state.json`/`reminders.json`. Для дубля в MAX им нужен
флаг платформы (`--platform max`, по умолчанию `telegram` — чтобы не
менять привычный вызов для боевой телеграм-волны), который выбирает файл
состояния/напоминаний и транспортный модуль. Логика отбора «зависших»
сессий (`lib/store.js`-независимая часть в `remind.js`) не меняется —
меняется только то, откуда читать и через что слать.

## Ограничения платформы MAX и как их обходим

- **Редактирование (`PUT /messages?message_id=…`)** — уточнено по
  документации (dev.max.ru, 14.08.2026), мягче, чем предполагал issue
  #26: в личных чатах сообщения с кнопками редактируются без
  ограничения по времени, без кнопок — если отправлены не позже 7
  суток назад; в группах/каналах — без ограничения всегда. Наши
  карточки почти всегда с кнопками — практического риска для якоря и
  карточек квиза нет даже при долгой паузе.
- **Удаление (`DELETE /messages?message_id=…`)** — временных
  ограничений в документации не указано вовсе (в issue #26
  предполагались те же 24 ч, что и для редактирования — не
  подтвердилось). Лимит на оба метода — не более 2 запросов/сек **в
  одном диалоге** (не путать с общим лимитом ниже). Транспорт всё
  равно глотает ошибки редактирования/удаления (см. «Архитектура»
  выше) — на случай редких неудач, а не как основная защита.
- **Лимит текста 4000 символов** (у телеграма — 4096) и **7 кнопок в
  ряду, 210 на сообщение** — с запасом укладываемся в текущие карточки
  квиза; стоит явно сверить самые длинные тексты (`lib/texts.js`) на
  этапе тестирования, вручную или расширением `bot/validate.js`.
- **Лимит 30 запросов/сек** (общий) — тот же порядок, что у телеграма,
  но формат ошибки/ретрая при 429 в документации не описан (только сам
  факт кода ответа). Это остаётся открытым вопросом, проверяется по
  факту при реализации `lib/max.js`.
- **Проверка подлинности вебхука** — `POST /subscriptions` принимает
  опциональный `secret` (5–256 симв.), который MAX кладёт в заголовок
  `X-Max-Bot-Api-Secret` каждого вебхук-запроса — аналог
  telegram-овского `X-Telegram-Bot-Api-Secret-Token`. `bot-max.js`
  должен сверять этот заголовок и отбрасывать запросы без совпадения.

## Дорожная карта к сентябрьской волне

0. Регистрация (готово, модерация пройдена) + DNS/nginx/certbot на VPS +
   пустой health-check вебхук, чтобы убедиться, что MAX достучался.
1. Регрессионные тесты на текущее поведение `bot.js` (см.
   «Тестирование» ниже) — **до** правок кода. Затем рефакторинг ядра:
   вынести `onMessage`/`onCallback`, убрать прямые
   `api("editMessageText", …)` и другие сырые вызовы, заменить на
   `editCard`/`answerCallback`/`setupCommands`. Трогает боевой
   телеграм-бот — тесты должны продолжать проходить, плюс ручная
   регресс-проверка на телеграме до мерджа.
2. `lib/max.js` (транспорт) + `bot-max.js` (вебхук-сервер).
3. `lib/store.js`: platform в uid-соли, раздельные
   `state.json`/`state-max.json`, `reminders.json` по платформе,
   `platform` в записях `answers.jsonl`.
4. Сквозной ручной прогон опроса в MAX от начала до конца (весь путь
   `intro → role → level → context → confirm → quiz → checkpoint →
   offer → done`, плюс `/pause`/`/resume`, исправление ответа).
5. `remind.js`/`notify.js` — флаг `--platform`; обновить
   `bot/README.md` и `RUNBOOK.local.md` разделами про MAX.
6. Пилот на небольшой группе перед общим анонсом волны (по аналогии
   с летним тестовым прогоном на 238 человек в телеграме).

## Тестирование

В проекте в целом юнит-тестов нет (см. `CLAUDE.md`), но рефакторинг
ядра `bot.js` (шаг 1) — риск для боевого телеграм-бота: он трогает код,
который сейчас работает без единой автоматической проверки. Это
целевое исключение из общего правила проекта, ограниченное этой
задачей — не прецедент для остального кода:

- **Перед** рефакторингом — набор регрессионных (характеризационных)
  тестов на текущее поведение `bot.js`: встроенный `node:test`
  (Node 22 уже на сервере и локально, без новых зависимостей — в духе
  «ноль зависимостей» проекта), транспорт (`lib/telegram.js`)
  мокается, тесты гоняют по внутреннему состоянию сессии и проверяют
  форму исходящих вызовов (`send`/`sendPhoto`/`hideCard`/`editCard`/
  `answerCallback`/…), а не реальные HTTP-запросы. Покрыть путь
  `intro → role → level → context → confirm → quiz → checkpoint →
  offer → done`, `/pause`/`/resume`, исправление ответа (`fix`),
  `/reset`.
- Тесты пишутся и проходят на **текущем** коде до начала рефакторинга,
  дальше рефакторинг ведётся так, чтобы они продолжали проходить —
  это и есть страховка от регрессии в телеграме.
- После рефакторинга те же тесты (с добавлением `lib/max.js`-стороны)
  переиспользуются как регрессионный набор для обеих платформ.
- `bot/validate.js` — расширить под MAX-специфичные ограничения (длина
  текста), если на шаге 4 найдутся нарушения.
- Основная ручная проверка остаётся: сквозной прогон в MAX (шаг 4) и
  ручной регресс-прогон в телеграме после рефакторинга (шаг 1) —
  автотесты дополняют её, не заменяют.
- Перед подключением `remind.js --platform max` к cron — обязательный
  `--dry-run` прогон, как и для телеграм-версии.

## Открытые вопросы

- Точный формат ошибок/ретрая MAX Bot API при превышении лимита
  запросов — уточняется на этапе реализации `lib/max.js` (шаг 2), не
  блокирует остальную подготовку.
