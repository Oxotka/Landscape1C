# Слой компетенций и грейдов — собранные исходники

> ## ⛔ Итог эксперимента (14.06.2026): слой грейдов заморожен
> Вывод после реализации и проверки: **для одной роли грейд почти повторяет шкалу зрелости** (базовое/продвинутое/нишевое) — это меры одного и того же («насколько инструмент продвинут»). Нового качества грейды дают лишь на единичных инструментах, а трудозатрат требуют много. Деление по аналогам проблему не решает (сложность аналога ≈ зрелость). Настоящую ортогональность дала бы только разметка вторых ролей (per-role), но это большой объём ради спорной отдачи.
> **Решение:** ветку `feature/competencies` в `main` не вливаем. Наработки оставляем как исследование — ценны независимо от грейдов: расшифрованная легенда матриц, сами матрицы, анализ покрытия ([`coverage.md`](coverage.md), там же находка про Linux-пробел и инструменты под чужими ролями).
> Всё ниже — материалы того эксперимента.

## Легенда отметок (РАЗРЕШЕНО)

Открытый вопрос из ТЗ про `v`/`ж`/`Ж` закрыт:

- **`V` / `v` — must** («ну прям очень ожидают»): уверенное знание, применение на практике, глубокие знания в предмете — условное погружение минимум на **60 %**.
- **`Ж` / `ж` — nice to have** («желательно»): понимание механики, принципов функционирования, решение элементарных задач — условное погружение на **~30 %**.
- В числовых матрицах вместо букв — **уровень требования 0–3** (в картинке закодирован цветом: красный 0, жёлтый 1, зелёный 2, синий 3).

> ⚠️ В листе «Программисты» регистр отметок непоследователен (встречаются и `V`/`Ж`, и `v`/`ж`). Считаем регистр незначащим: `v`=`V` (must), `ж`=`Ж` (nice to have). При формализации привести к одному регистру.

## Решения по шкале (согласовано)

**Стартуем только с роли «Разработчик».** Аналитики — позже отдельным этапом.

**Единая шкала — 4 ступени**, на базе официальной модели 1С (Junior/Middle/Senior) + надстройка Senior+:

| Наша шкала | Офиц. модель 1С | Весовая (7 грейдов) | Программисты / картинка (6) |
|---|---|---|---|
| **Junior** | Junior | Младший разработчик | Junior |
| **Middle** | Middle | Разработчик + Ведущий разработчик | Middle |
| **Senior** | Senior | Старший разработчик | Senior |
| **Senior+** | *(нет в модели)* | Архитектор + Ведущий архитектор | Архитектор + Эксперт |
| *не берём* | — | Руководитель практики | Лидерская функция |

Правила приведения:

1. **Разрешение конфликта при схлопывании столбцов** (Middle = Разработчик + Ведущий; Senior+ = Архитектор + Ведущий архитектор + Эксперт): берём **бóльшее** значение — «чтобы было куда стремиться».
2. **Senior+** делаем **без текстовых описаний** (офиц. модель заканчивается на Senior): показываем только список компетенций и инструментов. Если на этапе реализации будут сложности — допустимо ограничиться тремя ступенями (Junior/Middle/Senior).
3. **Лидерская функция / Руководитель практики не рассматриваем** — на этом уровне инструменты уже не профильны.

## Реализация (ветка feature/competencies)

- Грейд хранится в `data.js` как `item.grade = { разработчик: "junior|middle|senior|senior+" }`.
- Разметка генерируется скриптом **`scripts/grades.js`** (карта «категория/имя → грейд» + инвариант «нишевое не в Junior»). Источник правды по правилам — этот скрипт; `draft-grades.md` — человекочитаемый конспект.
  - `node scripts/grades.js` — dry-run (раскладка без записи);
  - `node scripts/grades.js --apply` — запись в `data.js`, затем `node scripts/cachebust.js`.
- Страница «Путь» (`app/path.js`): для ролей с разметкой `grade[role]` ступени = грейды, иначе фолбэк на шкалу зрелости.

## Остаётся определить при проектировании экрана

- **Числа vs отметки.** Весовые матрицы дают 0–3, отметочные — must/nice-to-have. Свести к одной модели при сборке данных.
- **Что показываем на сайте:** отдельный вид «Грейд» (выбрал уровень → компетенции + инструменты) или обогащение существующего вида «Путь».
